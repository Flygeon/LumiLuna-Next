# 给 LumiLuna 接入网易云账号：一场跨越六个小时的空响应鏖战

> 一次从「扫码登录」到「账号、歌单、云盘、播放」全部打通的功能开发实录。
> 文章里的每一步都是真实发生过的：那些看起来毫无道理的错误、反复推翻的结论、
> 最终被一行代码终结的谜团，还有差点把用户气跑的闪退。

---

## 背景

LumiLuna 是一个用 Tauri 2 + Vue 3 写的本地媒体播放器：扫盘、WebDAV、在线播放、逐字歌词……功能不算少。它原本的在线音乐能力依赖 meting 这类第三方代理 API——能用，但匿名、不稳定、不享受账号权益。

于是需求来了：**接入网易云账号，让用户能扫码登录、看到自己的账号信息、自己的歌单、云盘里的歌，并且能直接播放。**

前提约束很硬：

1. 登录态（cookie）必须留在 Rust 侧，不能进 WebView；
2. 不做独立页面，UI 融入现有的音乐选项卡，风格一致；
3. 设置里加一个开关；
4. 这台开发机没有 MSVC / Windows SDK，C 盘常年只剩 0~2GB——**本地编译是不可能的**，一切靠 GitHub Actions 远程构建。

参考项目是 [api-enhanced](https://github.com/neteasecloudmusicapienhanced/api-enhanced)，一个功能非常全的网易云 API 服务端。所有签名算法、请求头、风控对策都以它为准。

---

## 一、签名层：weapi / eapi / xeapi

网易云的前端接口大体分三套加密协议：

- **weapi**：网页端协议。双层 AES-128-CBC（外层随机 secretKey、内层固定 presetKey）+ RSA-1024 加密 secretKey。账号信息、歌单、云盘、搜索都走它。
- **eapi**：客户端协议。MD5 拼接 + AES-128-ECB。扫码登录、播放 URL 走它。
- **xeapi**：新一代客户端协议。X25519 密钥交换 + AES-128-GCM + HMAC-SHA256 + AES-ECB 三层加密。主要用于注册「匿名设备身份」。

Rust 侧要用纯 Rust 实现这三套，依赖 `aes`、`cbc`、`ecb`、`rsa`、`md-5`、`x25519-dalek`、`aes-gcm`、`hmac`、`sha2`、`flate2` 这些 crate。

### 第一个坑：RSA 公钥解析，直接闪退

网易云 weapi 用的 RSA 公钥是标准 SPKI 格式（`BEGIN PUBLIC KEY`）。我第一次用 `rsa::pkcs1::DecodeRsaPublicKey::from_pkcs1_pem` 解析——这玩意儿只认 `BEGIN RSA PUBLIC KEY`（PKCS#1 格式）。**运行期必然失败，而且我用了 `.expect()`，于是用户一点音乐选项卡，应用直接闪退。**

修复：改用 `rsa::pkcs8::DecodePublicKey::from_public_key_pem`，并且把命令路径上所有 `expect`/`unwrap` 换成错误传播。

### 第二个坑：Tauri 同步命令冻结 UI

Tauri 2 的同步命令跑在主线程，网络请求一卡就是整个窗口卡死。把所有网易云命令改成 `async fn` + `tauri::async_runtime::spawn_blocking`，把逻辑挪进 `*_sync` 内部函数。

### 第三个坑：扫码被风控拦截

第一个能跑的版本，扫码后手机端提示：**「检测到当前设备环境异常，本次操作已拦截」**，二维码轮询永远停在 801。

对照实验很快锁定了差异：参考项目启动时会用 xeapi 调 `/api/register/anonimous` 注册一个**匿名设备身份**（拿到 `MUSIC_A` cookie），之后的每个请求都带着它。我们的实现没有这一步——裸奔的请求直接被风控判定为异常环境。

于是移植 xeapi 协议。这个移植过程贡献了本场战役里最多的一批编译错误：

- `x25519-dalek` 2.x 的 `StaticSecret` 是 feature 门控的，要开 `static_secrets`；
- `try_into()` 链式调用类型推断失败，要显式标注 `let k: [u8; 16] = ...`；
- `encrypt_padded_vec_mut` 需要 cipher 的 `alloc` feature，默认没开，得手动分配 buffer 用 `encrypt_padded_mut`；
- `ecb` crate 的 trait 导入反复踩线。

还有一个**逻辑层面的坑**：xeapi 签名用的 HMAC 密钥，参考项目的 `crypto.js` 是直接把 base64 字符串的 UTF-8 字节当 HMAC key（Node `createHmac` 语义），我们却先 base64 解码再当 key——**签名从第一行起就是错的**，密钥接口永远返回空响应。对照源码逐行核实才发现。

匿名身份加上之后，**扫码终于能出二维码、能授权成功了**。以为要收工了——结果真正的噩梦才刚刚开始。

## 二、空 body 之谜：HTTP 200，0 字节

扫码授权成功后，下一步是拉账号信息（weapi `/api/w/nuser/account/get`）。然后用户发来一句轻飘飘的报错：

> 网易云响应解析失败(/w/nuser/account/get，HTTP 200，0字节):

**HTTP 200，响应体 0 字节。** 服务器「客气地」收下了请求，然后一个字都没回。

这个错误贯穿了后面六七个版本的构建，是我写过的最难缠的 bug。回头总结，它本质上是**几个真实缺陷的叠加**，而每一个单独修完都不足以让请求成功，所以排查过程极其漫长。

### 2.1 先修一批「看起来对」的问题

按出现的顺序，这些坑是一个个被排除的：

**坑：reqwest 不会自动带 Content-Type。** 参考项目用 axios 发 `URLSearchParams`，自动带 `Content-Type: application/x-www-form-urlencoded;charset=utf-8`；而 reqwest 的 `.body()` 什么都不带。服务器读不到表单参数，直接回空。补上之后，eapi 的 unikey 接口开始返回正常 JSON 了。

**坑：unikey 字段的位置。** 实测发现 unikey 在响应**顶层**（`{"code":200,"unikey":"..."}`），不在 `data` 下面。改了一行取值逻辑。

**坑：PEM 必须按 64 字符换行。** RSA 公钥从参考项目模板字面量里拷过来是一整行 216 字符——Node/OpenSSL 无所谓，但 Rust 的 `pem-rfc7468` 严格解码器要求**每行恰好 64 字符**，否则报 `invalid Base64 encoding`。下载 crate 源码逐行确认后，把公钥拆成 64/64/64/24 四行。

**坑：请求缺「特征」头。** 我们还加了随机中国 IP 头（`X-Real-IP` / `X-Forwarded-For`，对应参考项目 server.js 的 `global.cnIp` 逻辑）——海外/机房 IP 裸请求会被风控直接空响应，这是从源码里挖出来的对策。

**坑：RSA 填充模式。** 这是个大坑。参考项目的 `rsaEncrypt` 用的是 `node-forge` 的 `encrypt(str, 'NONE')`——我一度以为 'NONE' 是个无害的默认值，直到下载 node-forge 源码发现：

    } else if(['RAW', 'NONE', 'NULL', null].indexOf(scheme) !== -1) {
        scheme = {encode: function(e) {return e;}};   // 裸 RSA，无填充！
    }

**'NONE' = 无填充裸 RSA。** 我们用的 PKCS1v1.5 填充，服务端裸解密拿到带填充头的 128 字节，secretKey 提取失败。改成 `rsa::hazmat::rsa_encrypt`（直接 modpow），输出与 forge 完全一致。

**坑：双层 AES 的层序。** 参考实现是 `aesEncrypt(aesEncrypt(text,'cbc',presetKey,iv),'cbc',secretKey,iv)`——**presetKey 在内层、secretKey 在外层**。我们一开始写反了。修。

……修完所有这些，依然空 body。

### 2.2 方法论：让「应用自己交代」

到这里我意识到不能再靠猜了。这台机器上有一件利器：**参考项目（api-enhanced）可以本地跑起来，Node 也可以跑**。于是建立了一套「三对照」调试法：

1. **Node 复刻**：用 Node 把 Rust 的加密算法逐行复刻一遍，直接打真实接口。复刻版**永远成功**，返回完整的账号 JSON；
2. **curl 对照**：把请求参数导出，用 curl（schannel TLS）原样发送。也成功；
3. **应用实测**：永远失败，空 body。

三个实现，内容一模一样，只有应用失败。这是最折磨人的状态。

接下来做的几件事逐步缩小包围圈：

**给应用加「全量请求日志」**：每次请求把 URL、完整请求头（含 Cookie 全值）、请求体全文追加写到 appdata 下的 `netease-debug.log`。用户测完我直接读文件——彻底绕开了「用户肉眼转述 + OCR 乱码」这条失真通道。

**原样重放**：把应用日志里的请求用 Node **逐字节原样重放**——结果：**空 body**。然后把请求头/URL 原样保留、只替换成 Node 自己生成的 BODY——结果：**成功**。

> 结论锁定：应用生成的加密产物（params / encSecKey）**内容**是错的。长度对、格式对，但内容解不开。

**加加密自检**：让 Rust 在 weapi 加密后，用同一把密钥把密文解密回来验证。结果令人震惊：

    WEAPI-SELFCHECK 自检内层可解但外层失败：Invalid symbol 0, offset 0. 内层前40=0000000000000000000000000000000000000000

**用密钥解自己刚加密的密文，得到全 0。** AES 加密/解密不自洽——这在密码学上几乎不可能，除非实现有 bug。

**固定密钥复现**：为了排除随机性，加了一段用固定密钥（`AbCdEfGhIjKlMnOp`，16 字节）的复现加密，把 `text`、`inner`、`params`、解密结果全部打进日志。然后我看到了决定性的一幕：**两次请求的 text 不同（csrf_token 不同），加密出来的 inner 却完全相同。**

加密函数对「不同明文」输出「相同密文」——那它加密的到底是什么？

### 2.3 真相：一行代码的缺席

答案在 `cipher` crate 的 API 语义里。`encrypt_padded_mut` 是**就地接口**：

    fn encrypt_padded_mut<P>(self, buf: &mut [u8], msg_len: usize) -> Result<&[u8], PadError>

它把 `buf` 的**前 `msg_len` 个字节当作明文输入**，加密后写回 `buf` 开头。而我的代码是：

    let mut buf = vec![0u8; msg.len() + 16];   // 只分配了全 0 的 buffer
    let ct = enc.encrypt_padded_mut::<Pkcs7>(&mut buf, msg.len())?;

**明文从来没写进 buf。** 于是每一次加密的都是「全 0 的 61 字节」，两次请求当然产出相同的 inner；服务端拿到密文，解出来是 0，自然一个字都不想回。一切现象——包括自检解出全 0——全部自洽地指向这个事实。

修复只有一行：

    buf[..msg.len()].copy_from_slice(msg);   // 明文写入 buf 开头

然后，整个流程就通了。扫码、账号、歌单、云盘、播放，全部正常。

这个 bug 为什么这么难找？因为它藏在一个**几乎没人会细看的 API 语义**里：`encrypt_padded_mut` 不是「传入明文、返回密文」的经典函数式接口，而是「你把明文放进 buffer，我原地加密」的就地接口。而 Node 的 `createCipheriv`、参考项目的 CryptoJS 都是前一种语义——**用「正确实现的直觉」去写「就地接口」的代码，写出来的就是这种全 0 密文**。

顺带一提：eapi 之所以一直正常，是因为 eapi 用的 `aes_ecb_hex` 是逐块显式拷贝明文实现的，绕开了这个坑。同一套代码里，一个函数躲过了 bug，另一个踩得死死的。

## 三、插曲：把用户惹毛的闪退

排查进入白热化阶段时，我加了一个「固定密钥复现测试」，字符串随手写了个 `FixedSecret123456`——**18 个字符**。而 AES-128 密钥必须恰好 16 字节，`key.into()` 的 `GenericArray` 长度断言直接 panic。于是应用启动即崩，用户一句「打开扫码界面直接闪退，你到底能不能修好」差点把我送走。

这是我整场战役里最丢人的 bug：**调试代码自己写崩了生产代码**。教训：哪怕是一次性的调试代码，也要按生产标准检查边界条件。

## 四、没有本地编译环境的迭代是怎么活下来的

全程唯一能用的编译通道是 GitHub Actions（push 到 main 触发，Windows NSIS/MSI + Linux AppImage 双平台）。迭代循环长这样：

1. 本地改代码 → `git commit` → `git push`；
2. `gh run watch` 等 CI（每轮 6~9 分钟）；
3. 失败就看 `gh run view --log-failed` 抓编译错误；
4. 用户下载 artifact 实测 → 反馈报错 → 回到 1。

这中间还有一堆环境的坑：git push 走 schannel 经常 TLS 握手失败，得重试或临时 `GIT_SSL_NO_VERIFY`；机器上有 Clash 代理（127.0.0.1:7890），代理没开时直连 github 失败，开了之后 push 要走代理（`git config http.proxy`）；`gh` 走代理会随机 EOF，得改用 curl 查 GitHub API；一度怀疑用户跑的是旧构建，靠比对 artifact 大小和 exe SHA256 才确认用户确实装的是最新版……

**效率最高的动作，是把「用户肉眼 + OCR 转述」换成「应用自己写日志、我直接读文件」**。从那之后，每一轮测试都能拿到应用实际发送的完整请求，排查速度完全不一样了。

## 五、复盘

这场仗打下来，值得记住的几点：

1. **API 语义比算法本身更容易出错。** 加密算法移植最大的风险不是算法写错，而是「你以为的接口行为」和「实际接口行为」不一致。`encrypt_padded_mut` 的就地语义、`pem-rfc7468` 的 64 字符限制、`forge 'NONE'` 的裸 RSA——全是这类问题。**下载 crate 源码逐行确认，比相信直觉快得多。**

2. **让程序自己交代，别让用户转述。** 一旦陷入「用户报错 → 我猜 → 改 → 再报错」的循环，立刻停下来做自证：日志、自检、固定输入复现、原样重放。每一层自证都把问题的包围圈缩小一层。

3. **「同一个逻辑，A 实现成功、B 实现失败」时，差异一定藏在某个你没对比过的字节里。** 把它找出来的办法就是逐字段对比——直到把「内容」全比完，剩下的只有「内容本身」。

4. **心态：这种 bug 不是靠聪明解决的，是靠把怀疑对象一个个钉死排除掉的。** 六个小时里大部分时间在做排除法，真正动手改代码的时间可能不到半小时。

5. **调试代码也是代码。** 18 字符的密钥能闪退整个应用，提醒我：debug 代码的边界条件，和生产代码一样重要。

最终，用户说「能用了」。那三个字，比任何一个技术结论都值钱。
